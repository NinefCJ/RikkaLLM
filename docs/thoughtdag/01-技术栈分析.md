# 01 · 技术栈分析

> 本文档分析 **RikkaLLM**（Gradle `rootProject.name = rikkahub`，应用包名 `com.ninef.rikkallm`）当前使用的技术栈，并与参照项目 **ThoughtDAG** 做差异对比，为后续"DAG 上下文图 + 可视化画布"改造提供基线。

---

## 1. 模块总览与依赖方向

项目采用多 Gradle 模块（`settings.gradle.kts` 中的 `include`）分层，依赖方向为：

```
common → ai / speech / search → app
（document、highlight、material3、web、workspace、mnn 按能力挂载）
```

| 模块 | 命名空间 | 类型 | 角色 | 关键依赖 |
|---|---|---|---|---|
| `app` | `com.ninef.rikkallm` | Android 应用 | 主应用：UI、ViewModel、数据层、编排逻辑 | 依赖全部业务模块 |
| `ai` | `me.rerere.ai` | Kotlin/JVM | AI 抽象核心：`UIMessage`、`Provider`、`Tool`、`Model` | 仅依赖 `:common` |
| `common` | `me.rerere.common` | Kotlin/JVM | 通用工具：缓存、HTTP/SSE、QuickJS、Android 上下文 | 无业务依赖 |
| `document` | `me.rerere.document` | JVM | 文档解析（PDF/DOCX/PPTX/EPUB） | — |
| `highlight` | `me.rerere.highlight` | Compose | 代码高亮 | Compose |
| `material3` | `me.rerere.material3` | Compose | 定制 Material3 颜色工具 | Compose |
| `search` | `me.rerere.search` | Kotlin | 搜索 SDK（Exa/Tavily/Zhipu/Bing/Brave/SearXNG…） | `:ai`、`:common` |
| `speech` | `me.rerere.speech` | Kotlin | TTS / ASR | `:common` |
| `web` | `com.ninef.rikkallm.web` | Android | Ktor 本地服务器 + SSE + JWT，托管 `web-ui/` 构建产物 | Ktor |
| `workspace` | `me.rerere.workspace` | Android | Agent 工作区沙箱（CMake 原生 + shell 执行） | `:common` |
| `mnn` | `com.ninef.rikkallm.mnn` | Android | 本地 MNN 推理引擎（预编译 `libMNN.so`） | NDK/CMake |

## 2. 技术栈分维度清单

### 2.1 前端 / UI 框架
- **Jetpack Compose**（声明式 UI），Material3 + 项目内 `material3` 定制主题（如 `Radius`、`Spacing`、深色模式 `LocalDarkMode`）。
- 图标库 `me.rerere.hugeicons`（`HugeIcons`）。
- 富文本/图渲染：**WebView 承载 `mermaid.min.js`**（`Mermaid.kt`，资源在 `app/src/main/assets/html/mermaid.min.js`，约 3.4MB）；`DiagramRenderer.kt` 通过 workspace 内 `pdflatex` 编译 LaTeX 图表为 SVG。
- 导航：**Navigation 3（Compose 版 Navigation）**，路由在 `app/src/main/java/com/ninef/rikkallm/Screen.kt` 以密封类 `Screen` 定义。

### 2.2 后端 / 本地服务
- **Ktor**（`web` 模块）：本地 HTTP 服务器，提供 SSE 与 JWT，托管 React `web-ui` 静态资源（构建于 `web-ui/`，需 `pnpm`）。
- 真正的"模型后端"是外部 LLM Provider（OpenAI / Google / Claude / LocalServer / Ollama 兼容），通过 `ai` 模块的 `Provider` 接口抽象。

### 2.3 数据库 / 持久化
- **Room**（KSP 代码生成），数据库类 `AppDatabase`，`version` 较高（schema 目录 `app/schemas/.../AppDatabase/N.json` 已迁移至 `com.ninef.rikkallm.data.db.AppDatabase`）。
- 消息以 **JSON 列** 存储：`ConversationEntity` 含 `nodes` 列存放 `messageNodes`；`message_node` 表含 `messages` JSON 列。`MessageNodeDAO` 利用 `json_each()` 做 token 统计（`RawQuery`）。
- 配置类数据用 **DataStore**（`Settings` 等）。

### 2.4 状态管理
- **Koin** 依赖注入（`app/src/main/java/com/ninef/rikkallm/di/`：`AppModule`、`ViewModelModule`、`RepositoryModule`、`DataSourceModule`、`PluginModule`、`MnnLocalModule`、`editorModule`）。
- **ViewModel + StateFlow/MutableStateFlow + Compose `collectAsState`** 驱动 UI。
- 数据流以 **Kotlin `Flow`**（Room `Flow`、Koin `single` 仓库）贯穿，分页用 **Paging3**（`PagingSource`）。

### 2.5 异步 / 并发
- **Kotlin Coroutines + Flow**；SSE 流式响应通过 `flow {}` 暴露。
- IO 密集操作用 `Dispatchers.IO`（`withContext`）。

### 2.6 构建工具
- **Gradle + Kotlin DSL**；约定插件集中在 `build-logic/`（`rikkahub.android.library` / `rikkahub.android.application` 等）。
- 编译期代码生成：**KSP**（Room、序列化）、**kotlinx-serialization**（模型 `@Serializable`）、**Compose Compiler**（编译器配置 `app/compose_compiler_config.conf`）。
- `:mnn` 依赖 `vendor/MNN` 与预编译 `libMNN.so`，通过 `scripts/setup-mnn.*` 准备。

### 2.7 AI / 模型抽象
- `ai` 模块：`Provider<T : ProviderSetting>` 接口（`listModels`/`generateText`/`streamText`/`generateEmbedding`/`generateImage`），实现：`OpenAIProvider`、`GoogleProvider`、`ClaudeProvider`、`LocalServerProvider`。
- 消息模型：`UIMessage`（`id`/`role`/`parts`/`annotations`/`createdAt`/`finishedAt`/`modelId`）+ `UIMessagePart` 密封类（`Text`/`Image`/`Video`/`Audio`/`Document`/`Reasoning`/`Tool`/`ToolResult`/`GenerativeCard`）。
- 工具调用：`UIMessagePart.Tool`（`toolCallId`/`toolName`/`input`/`output`/`approvalState`），支持用户审批 `ToolApprovalState`。
- 消息变换管线：`InputMessageTransformer` / `OutputMessageTransformer`（`transform` / `visualTransform` / `onGenerationFinish`）。

## 3. 与 ThoughtDAG 的技术特征差异

| 维度 | RikkaLLM（现状） | ThoughtDAG（参照） | 启示 |
|---|---|---|---|
| 形态 | Android 移动 App（Compose） | 本地优先桌面工具（macOS/Win/Linux，内置本地引擎） | 复用移动端已有的 Compose 能力即可做画布 |
| 上下文模型 | **线性**：`currentMessages = node.messages[selectIndex]` 按节点顺序拼成序列 | **DAG**：节点=消息/来源/推理路径，**边即上下文**，遍历入边构建序列 | 现状是 DAG 的"退化特例"，改造平滑 |
| 分支能力 | `MessageNode.messages` 列表内 `selectIndex` 切换"重生成版本" | Branch/Prune/Merge/Inspect 四类图操作 | 现有 `ChatMessageBranch` 已是 Branch 雏形 |
| 上下文预览 | 无 token 级预览/对比 | Inspect 预览 + Context diff（删边显示 "−N tokens"） | 需在流式前插入 `ContextAssembler` |
| 来源溯源 | `UIMessage.annotations` / `metadata` 有扩展位但未体系化 | provenance：片段级溯源、Ask from source | 复用 `annotations`/`metadata` |
| 渲染 | WebView + mermaid.min.js（静态图）、pdflatex（SVG） | 自绘/引擎内画布（可交互） | 交互画布应**避免 WebView**，用 Compose Canvas 自绘以保轻量 |
| 部署重量 | 已含 MNN 原生、web-ui、jieba 字典等（debug APK ~94MB） | 轻量、本地优先、无 Node/终端 | "轻量化"应**不新增重型库**，复用既有 Compose/Koin/Room |

**结论**：RikkaLLM 的基础设施（Compose、Koin、Room、Provider 抽象、Transformer 管线、`ChatMessageBranch`）已覆盖 ThoughtDAG 所需 80% 的底座；改造重点是"把线性 `currentMessages` 升级为可遍历的 DAG 序列"，而非引入全新框架——这正是"轻量化部署"得以成立的根因。
