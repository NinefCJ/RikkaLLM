# 03 · 可扩展点识别

> 本文档定位 RikkaLLM 现有架构中，适合插入"DAG 上下文图 / 任务编排 / 可视化画布"的模块与层次，并说明每个挂点的改造方式与风险。

---

## 总览图

```
                   ┌─────────────────────────────────────────────┐
   UI 层           │ ChatPage / ChatMessageBranch / Mermaid(WebView) │
                   └───────────────┬───────────────┬───────────────┘
                                   │ 入口/交互        │ 画布入口
                   ┌───────────────▼───────────────▼───────────────┐
   状态/ViewModel  │ ChatVM + Repository（Koin 注入）               │
                   └───────────────┬───────────────────────────────┘
                                   │ 组装/读取
                   ┌───────────────▼───────────────────────────────┐
   编排/生成层     │ GenerationHandler.generateText( )              │
                   │   ├─ 上下文序列计算  ◀── 挂点① currentMessages │
                   │   ├─ InputTransformer 管线  ◀── 挂点③          │
                   │   ├─ provider.streamText( )                    │
                   │   └─ OutputTransformer 管线 (.transforms) ◀挂点 │
                   └───────────────┬───────────────────────────────┘
                                   │
                   ┌───────────────▼───────────────────────────────┐
   持久化层        │ Room: ConversationEntity / message_node 表      │
                   │   ◀── 挂点⑤ 新增 GraphNode/GraphEdge 实体       │
                   └───────────────────────────────────────────────┘
   AI 抽象层       │ Provider / Model / Tool（挂点④ 工具回环复用）   │
```

---

## 挂点①：上下文序列计算（`Conversation.currentMessages`）

- **位置**：`app/.../data/model/Conversation.kt`
- **现状**：`messageNodes.map { it.messages[it.selectIndex] }`，线性、按节点顺序、各取一个选中版本。
- **改造**：新增 `GraphContext` 概念——每个 `MessageNode` 声明其**父节点集（入边）**；`currentMessages` 改为"从目标节点沿入边做拓扑遍历，按拓扑序收集祖先的选中版本"。
- **风险/收益**：收益最高（直接决定发给模型的上下文）；风险是需保证 DAG 无环（写入时校验）。**建议保留 `currentMessages` 作为"无图模式"的向后兼容路径**。

## 挂点②：装配前 Hook（GenerationHandler）

- **位置**：`app/.../data/ai/GenerationHandler.kt` `generateText(...)` 中"组装请求序列"处。
- **改造**：在调用 `provider.streamText` 之前，交由新增的 **`ContextAssembler`** 生成"将发送的序列"，并产出 `ContextPreview`（含 token 估算、各节点来源、可预览的 diff）。
- **收益**：与现有 `maxSteps` 工具循环天然契合——编排器可在每一步重算上下文。

## 挂点③：Transformer 管线

- **位置**：`app/.../data/ai/transformers/Transformer.kt` 的 `transforms/visualTransforms/onGenerationFinish`。
- **改造**：
  - 新增 `GraphContextTransformer`（Input）：注入来源溯源 `annotations`、按图结构重排消息。
  - 复用 `ThinkTagTransformer`/`RegexOutputTransformer` 等，不改既有行为。
- **收益**：完全遵循既有扩展范式，零侵入。

## 挂点④：工具回环（编排复用点）

- **位置**：`GenerationHandler.generateText` 的 `for (stepIndex in 0 until maxSteps)` 循环，`Tool` 执行与 `ToolResult` 回填。
- **改造**：DAG 编排器的"节点依赖就绪 → 执行 → 产出 → 触发下游"状态机，可复用同一套 **工具执行 + 结果回填** 机制。即"任务编排"不必另起炉灶，而是把 `Tool` 抽象提升为"图节点执行单元"。
- **收益**：任务编排与聊天生成共用执行内核，轻量化。

## 挂点⑤：持久化层（Room）

- **位置**：`app/.../data/db/dao/{ConversationDAO,MessageNodeDAO}.kt`、实体、`AppDatabase`。
- **现状**：`message_node` 表以 `messages` JSON 列存储；`MessageNodeDAO` 用 `json_each()` 做 token 统计（`RawQuery`）。
- **改造**：新增 `GraphNodeEntity` / `GraphEdgeEntity` + `GraphDAO`，遵循 `Flow` / `suspend` / `RawQuery` 既有模式；`AppDatabase` 升 version 并迁移。
- **收益**：图数据可独立查询、可分页、可统计 token，与现有统计能力无缝衔接。

## 挂点⑥：UI 层（入口与交互）

- **位置**：
  - 路由 `app/.../Screen.kt`（密封类 `Screen`）。
  - 分支 UI `app/.../ui/components/message/ChatMessageBranch.kt`（`ChatMessageBranchSelector`，已支持左右切换版本）。
  - 图渲染 `app/.../ui/components/richtext/{Mermaid,DiagramRenderer}.kt`（WebView/mermaid、pdflatex-SVG）。
- **改造**：
  - 在 `Screen` 增加 `Screen.GraphCanvas(conversationId)` 路由，从 `ChatPage` 顶栏按钮进入。
  - `ChatMessageBranch` 作为 Branch/Prune 的"气泡内快捷操作"基础。
  - **画布本身不复用 WebView（mermaid）**：交互式拖拽/连线需在 Compose 内用 **`Canvas` + `pointerInput` 手势自绘**，mermaid 仅用于"导出静态图"。

## 挂点⑦：本地服务（导出/协作）

- **位置**：`web` 模块（Ktor 本地服务器）。
- **改造**：图可序列化为 Mermaid/JSON，经 `web` 模块或 `WebView` 预览/分享。**非必需**，列为 P2。

---

## 改造侵入度评估

| 挂点 | 侵入度 | 是否必改 | 备注 |
|---|---|---|---|
| ① currentMessages | 中 | 是（核心） | 加图遍历分支，保留旧路径兼容 |
| ② GenerationHandler | 低 | 是 | 注入 ContextAssembler |
| ③ Transformer | 低 | 否 | 可选增强 |
| ④ 工具回环 | 低 | 否 | 编排复用，不强制 |
| ⑤ Room | 中 | 是 | 新增实体+迁移 |
| ⑥ UI | 中 | 是 | 新增画布页+交互 |
| ⑦ web | 无 | 否 | P2 导出 |

**结论**：核心改造集中在 ①⑤⑥（数据模型 + 持久化 + UI），② 为编排粘合点，③④ 为可选增强、复用既有机制——整体侵入可控，符合"轻量化"诉求。
